##  Уроки пользования GitHub
### Создание новой ветки и подготовка к Pull Request состоит из нескольких простых шагов в терминале.

1. Переход в базовую ветку
Убедитесь, что вы находитесь в актуальной ветке main, от которой будете наследоваться:

   **git checkout main** или 
 
   **git pull origin main** (для подтягивания последних обновлений с сервера)

2. Создание и переход в новую ветку
Создайте новую ветку (например, для второй лабораторной работы назовем ее lr2) и сразу переключитесь на нее с помощью флага -b:

   **git checkout -b lr2**

3. Написание кода и фиксация изменений
Теперь вы работаете в изолированной ветке lr2. Добавляйте новые файлы, пишите код, а затем сохраните изменения стандартным способом:

   **git add .**

   **git commit -m "Реализация REST API для второй лабораторной"**

4. Первая отправка ветки на сервер
Так как ветки lr2 еще нет на удаленном сервере, при первой отправке нужно связать локальную ветку с удаленной с помощью флага -u:

   **git push -u origin lr2**

   В дальнейшем при работе в этой ветке будет достаточно писать просто **git push**.

5. Создание Pull Request в браузере
После успешной отправки зайдите на страницу вашего репозитория (в GitHub, GitLab или другой системе). Там автоматически появится всплывающее уведомление и кнопка "Compare & pull request" (или "Create merge request"). Нажмите на нее, убедитесь, что базовой веткой (base) указана main, а веткой сравнения (compare) — lr2, и подтвердите создание запроса на слияние.

## Проверка работающего API через Postman

Пока Uvicorn запущен, откройте Postman. Для каждого запроса выберите HTTP-метод, укажите URL, при необходимости заполните **Body** и нажмите **Send**. Внизу Postman покажет статус и тело ответа; в окне Uvicorn появится строка с методом, маршрутом и статусом. Базовый адрес проекта: `http://127.0.0.1:8000`. Для повторного прохождения сценария используйте новые логин и паспорт: эти поля уникальны в БД.

### Шаг 1. Сервер отвечает

Отправьте `GET http://127.0.0.1:8000/`. Ожидается **200 OK** и приветственное JSON-сообщение. Так проверяется доступность HTTP-сервера; работа регистрации и БД этим запросом ещё не доказана.

### Шаг 2. Регистрация клиента

Отправьте `POST http://127.0.0.1:8000/auth/register`. Выберите **Body → raw → JSON** и вставьте:

```json
{
  "username": "student_test_1",
  "password": "strong-pass",
  "role": "client",
  "client": {
    "full_name": "Иванов Иван",
    "date_of_birth": "1990-01-01",
    "passport_info": "test-passport-1",
    "contact_phone": "+79991234567"
  }
}
```

Ожидается **201 Created**, в ответе — `id`, `username`, `role: "client"`; пароля и хеша нет. Запрос проходит через Pydantic `UserCreateAuth`, `register()` и SQLAlchemy и создаёт в БД учётную запись вместе с профилем клиента. Повтор того же логина даст `400`, повтор паспорта с другим логином — `409`. При повторном запуске теста смените оба значения.

### Шаг 3. Вход и получение JWT

Отправьте `POST http://127.0.0.1:8000/auth/login`. Выберите **Body → x-www-form-urlencoded**, создайте две строки:

| Key | Value |
|---|---|
| `username` | `student_test_1` |
| `password` | `strong-pass` |

Ожидается **200 OK** с `access_token` (длинная строка JWT) и `token_type: "bearer"`. Скопируйте значение `access_token` без кавычек. При неверном пароле ожидается `401`. Здесь выполняются поиск `User`, проверка bcrypt-хеша и создание JWT; пароль не попадает в JWT.

### Шаг 4. JWT обязателен для чтения клиентов

Отправьте `GET http://127.0.0.1:8000/clients/` **без** авторизации: ожидается **401 Unauthorized**. Затем откройте в Postman вкладку **Authorization**, выберите **Type: Bearer Token**, вставьте клиентский `access_token` в поле **Token** и повторите запрос. Теперь ожидается **200 OK** и список только с профилем этого клиента. Для каждого следующего защищённого запроса выбирайте нужный токен: клиентский или агентский. Если токен испорчен либо истёк, ответ снова `401`.

### Шаг 5. Клиент не может создавать продукты

С **клиентским** Bearer-токеном отправьте `POST http://127.0.0.1:8000/products/`, **Body → raw → JSON**:

```json
{"name":"КАСКО","type_of_insurance":"Авто","basic_tariff":5.5}
```

Ожидается **403 Forbidden**. Личность установлена, но роль клиента не разрешает запись продукта. Запомните различие: `401` означает отсутствие действительной аутентификации, `403` — пользователь известен, но действие ему запрещено.

### Шаг 6. Регистрация агента и повтор продукта

Для агентской регистрации у процесса сервера должна быть переменная `AGENT_REGISTRATION_CODE`. Если её не задавали, остановите Uvicorn сочетанием `Ctrl+C`, затем в **том же окне PowerShell** введите:

```powershell
$env:AGENT_REGISTRATION_CODE = 'agent-secret-123'
uvicorn main:app --reload
```

В Postman отправьте `POST /auth/register`, **Body → raw → JSON**:

```json
{
  "username": "agent_test_1",
  "password": "strong-pass",
  "role": "agent",
  "agent": {
    "full_name": "Петров Петр",
    "position": "Агент",
    "department": "Продажи"
  },
  "agent_code": "agent-secret-123"
}
```

Ожидается **201 Created**. Неверный `agent_code` даст `403`. Затем выполните `POST /auth/login` с `username=agent_test_1`, `password=strong-pass`; скопируйте **новый токен агента**. Если сервер перезапускался без постоянного `JWT_SECRET_KEY`, старые JWT перестанут действовать, поэтому для дальнейших клиентских запросов войдите клиентом ещё раз.

С агентским токеном повторите `POST /products/` с JSON из шага 5. Ожидается **201 Created** и `id` продукта. Это показывает запись в БД и проверку роли.
